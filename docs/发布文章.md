## 导语

我们习惯说「它记得我」，但很少有人能回答：它到底记得什么？

在数据库里，记忆是一行行文本：时间、重要度、强度、向量。这些字段对人来说不构成「记得」。
直到把它们放进空间——谁和谁相连、哪些在中心、哪些正在变灰——「它记得我」才第一次有了形状。

这篇文章讲我怎么把一份聊天机器人的记忆做成三维星云：为什么选力导向图、每个视觉元素
对应哪个字段、两份记忆库怎么合并、权限怎么裁、性能怎么压，以及踩过的六个坑。

## 一、起因：记忆不是「存不下」，是「看不见」

这个项目最初只是一个 QQ 机器人的附属页面。机器人有两条记忆链路：

- **共用记忆**：每一轮问答都实时写入，量大，另一个端也在读；
- **本地伴生**：夜间整理时提炼事实、情绪和向量，有强度、有半衰期。

数据一直在长，但主人能用的只有「召回」：对话时挑几条塞进提示词。于是问题来了：

- 记错了没法改，只能等新记忆覆盖；
- 想不起某件事是在哪次对话里说的；
- 不知道哪些记忆快被遗忘了，哪些被标成了永久；
- 两份库各自为政，看不出「同一个人」在两边是不是一回事。

所以第一版目标很具体：**给主人一面能照见记忆的镜子**，而不是再做一个后台表格。

## 二、它长什么样

打开页面，是一张深色的三维星云。

- **球**是数据：核心、人格、会话、日期、消息、摘要、记忆，七类；
- **大小**是重要度：越重要的记忆球越大；
- **灰度**是遗忘程度：`强度 = 0.5^(天数/半衰期)`，半衰期 `7 + 83×重要度` 天；
- **紫红色**是永久记忆：强度锁 1.0，夜间遗忘不动它；
- **线**是关系：拥有、归属、活跃、摘要、替代、语义相似，多种关系自动弯成弧线；
- **流动的光点**表示「关系在动」：摘要和摘要语义相近时，青色粒子沿着线跑。

空间上分三层同心圈：核心 94、熟识 176、陌生 304。关系近的人在内圈，陌生人在外圈形成星环。
力导向只负责圈内微调，所以「谁离你近」是稳定的，不会因为某天多聊几句就把人甩到图外。

页面上的操作都对应真实痛点：

| 功能 | 解决什么 |
|---|---|
| 搜索 | 记得一句话，想不起属于谁 |
| 看谁 | 人一多图太密，只看一个人并自动框住 |
| 时间轴 | 想找「上个月」的事 |
| 图例筛选 | 消息球太多挡住记忆球 |
| 详情面板 | 看全文、来源、重要度、时间 |
| 多选 | 一次忘掉/永久/合并一批 |
| 同步 | 改完立刻重建，不用等 30 分钟 |
| 导出 | 备份成 JSON |

## 三、六个设计决策

### 1. 为什么是三维力导向图

比较过表格、时间线、二维网络图。表格精确但看不出关系；时间线只有一维；二维图边一多就糊。
三维力导向同时做到三件事：聚类自然、纵深分层、可探索。代价是遮挡和眩晕，所以补了自动取景、
悬停压暗、回中心和「星云模式」。

### 2. 视觉编码只表达一件事

颜色只编码类型，大小只编码重要度，灰度只编码强度。早期试过用颜色深浅表示强度，
结果和「永久」的紫红打架。拆成两个维度后，图立刻好读了。

### 3. 两份库，一种 id

图里的记忆 id 是 `mem:<库>:<id>`：`mem:s:9` 是共用记忆，`mem:b:9` 是本地伴生。
前端不用知道有几个库，只传 id；服务端按前缀路由，顺便把毫秒/秒两种时间单位统一。

### 4. 语义边不能 O(n²)

两两算余弦，1000 条要 27 秒。做法是三层控制：每 8 维取一维粗排、粗排过线才算全量、
记忆只比最近 120 条。相似度还做了基线校正 `(cos-0.45)/0.55`，和召回同一套口径。
向量用 base64(float32) 缓存，比 JSON 数组小约 5 倍。

### 5. 权限分三层，抹掉和裁剪是两条路

- **本机**：只绑 127.0.0.1，全权；
- **访客**：保留完整拓扑，正文全部抹掉，没有编辑入口；
- **账号**：一人一号。**每个人都能登录进来，查看并操作自己的那一份**——改正文、调重要度、
  忘掉/恢复、设为永久、删除、合并，改完立刻重建；导出也只导出自己的。别人的球还在图上
  （所以能看到「这个人有多少记忆」），但点开只有一句「别人的记忆」，没有正文。
  服务端还会逐条校验归属，越权直接 403。

换句话说，它不是一个「只读橱窗」：**每个被邀请的人都有自己的操作台**，只是操作台之间
互相看不见内容。管理员额外拥有全站视图、账号管理和能力开关。

「抹掉」和「裁剪」分开，是为了让访客也能看到星云的形状，而不是一片空白。

### 6. 零依赖

Python 标准库起 HTTP 服务，前端两个本地库（3d-force-graph、Pico CSS），不装数据库、
不装 Node、不连 CDN。代价是单文件 HTML 约 2600 行，好处是改完刷新即生效。

## 四、性能：首屏从 1.7MB 到 0.45MB

- 超过 1KB 的 HTML/JSON 响应现场 gzip：首页 71KB→25KB，图 263KB→47KB；
- vendor 预压缩成 `.gz`，命中直接发：1.39MB→364KB；
- `vendor/*` 长缓存 + `?v=N` 换版本，页面本身 `no-store`；
- `graph.json` 先写临时文件再原子替换，重建时刷新也不会读到半个 JSON。

300~400 个节点仍然流畅。再大就要按人裁剪或增量渲染，这是下一步。

## 五、隐私：默认别人连不上

这是个人数据，默认配置必须「别人连不上」：

- 默认只监听 `127.0.0.1`；
- 写接口要求 `X-Viewer: 1`，配合 CSP 和 `SameSite=Lax` 挡 CSRF；
- 密码 PBKDF2-SHA256（20 万次迭代），登录按 QQ 限流；
- 访客和普通账号拿不到别人的正文、昵称，导出也只导出自己的；
- 会话只存 SHA-256，默认 7 天过期。

**明文 HTTP 是明确边界**：局域网模式不加密，公网请套 HTTPS 反代或组网工具。

## 六、踩过的六个坑

1. `nodeOpacity(fn)` 不生效——这个版本只收数字，传函数会让所有球变透明，看起来像黑屏；
2. `backgroundColor('rgba(0,0,0,0)')` 会变纯黑，把 CSS 星尘全盖住；
3. 不要用 PowerShell 的 `Set-Content` / `-replace` 改源码，中文会变乱码；
4. `graph2ScreenCoords()` 返回的坐标是错的，叠加层要自己算投影矩阵；
5. 镜头不会自动取景：初始距离 320，图能到 ±400，必须手动 `zoomToFit()`；
6. 换 vendor 的 JS 要同时重做 `.gz` 并改 `?v=`，否则缓存对不上。

## 七、局限与下一步

- vendor 是 UMD 包，没暴露 `THREE`，做不了 bloom 和自定义着色器——下一步换 ESM 版；
- 全量重建，数据再大需要增量；
- 会话在内存里，重启要重新登录；
- 只有 QQ 这一种接入，其他模型/平台要自己接数据源。

## 八、怎么跑起来

需要 Python 3.9+，没有第三方依赖：

```bash
python demo/make_demo.py     # 造一套虚构演示数据
python viewer_server.py 8765
```

打开 `http://127.0.0.1:8765/`。换成真实数据时，放入 `bridge.db` / `brain.db`、`data/`、
`personas/`，跑一次 `python memory_view.py` 即可。

仓库里带了自检脚本：`tools/check_repo.py` 核对文档、接口、导入、脚本是否互相对得上，
`tests/smoke_test.py` 真起服务走一遍。提交前跑一次，避免「文档说得出、仓库里找不到」。

## 附：评论区 Q&A 回复模板

**Q：为什么不用 Neo4j / 图数据库？**
A：数据量只有几百到几千条，SQLite 够用；我要的是「主人能看懂的一张图」，不是通用图查询。
多引入一个数据库，部署成本反而更高。

**Q：会把我的聊天记录传到哪里吗？**
A：不会。服务默认只绑 127.0.0.1，数据都在本地 SQLite 和 JSON 里；访客模式连正文都不返回。

**Q：支持其他模型 / 平台吗？**
A：页面只认 `graph.json` 的结构。只要能把数据导成两份库或直接生成 graph.json，就能接。

**Q：手机能用吗？**
A：能，窄屏会收进抽屉，详情变底部面板；WebGL 性能取决于手机。

**Q：为什么不做成 SaaS？**
A：记忆是最私人的数据。这个项目的默认值是「数据留在你自己的机器上」。

**Q：永久记忆是什么？**
A：`pinned=1`。强度锁 1.0、不受夜间遗忘影响、每次对话都进提示词——等于写进那个人的档案。
