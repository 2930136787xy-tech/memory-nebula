# 记忆引擎 · 方法与处理说明

整理时间：2026-10-31
适用代码：`仓库根目录`（`companion_brain.py` / `memory_view.py` / `viewer_server.py` / `data_backup.py`）

这份文档回答三个问题：**每次对话时记忆是怎么被找出来的**、**新事实进来时旧事实怎么处理**、**这些规则凭什么这么定**。所有数字都来自本机实测，不是估的。

---

## 0. 一句话总览

一句话：**两路召回（语义 + 字面）→ 合成一个分 → 过滤过期 → 规则重排 → 证据不足就拒答 → 去重去冗余 → 顺边联想 → 落一行日志**。

```
用户一句话
   │
   ├─ 语义通道：查询向量 × 每条记忆向量（numpy 一次矩阵乘）
   ├─ 字面通道：SQLite FTS5（中文双字切分 + IDF 覆盖率门控）
   │
   ├─ 查询分流：推理型问句 → 只用语义通道
   │
   ├─ 合成打分：相关度 + 重要度 + 新近度 + 情绪 + 环 + 核心层 + 永久
   ├─ 有效期过滤：valid_to 已过的不参与
   ├─ 规则重排：整句命中 +0.12、双字覆盖 ×0.10（只看前 20）
   ├─ 拒答门控：最高分 < 0.42 且前三挤在一起 → 当作"没印象"
   ├─ MMR：按层配额去冗余（核心层优先，永久记忆必留）
   └─ 差序联想：从已选前两条走一跳共现/演化边，最多补 2 条
        │
        └─ 写 data/recall-debug.log 一行：候选数、选中数、查询
```

## 2. 两条通道

### 2.1 语义通道

- 记忆向量存在 `mem_vec` / `memories.vec`，查询向量现算。
- 一次 numpy 矩阵乘算全部相似度（19 条时 0.3 ms，纯 Python 逐个算要 3 ms）；numpy 不可用时退回 `_cos` 逐条。
- 归一化公式见上表；云端 `text-embedding-v3` 与本地 `bge-small-zh` 都适用同一基线。

### 2.2 字面通道（FTS5）

| 设计点 | 做法 | 原因 |
|---|---|---|
| 切分 | 中文双字 + 单字，都进索引 | SQLite 默认分词器不切中文 |
| 查询侧 | 有双字就丢掉单字 | 单字命中太泛，"的/了"能把整库捞出来 |
| 覆盖率门控 | 查询词在正文里的 IDF 加权占比 < 0.03 丢弃 | bm25 是按本次最高分归一化的，永远有第一名，单看它判不了"不相关" |
| 增量索引 | 新记忆写入时同步进 `mem_fts`，`meta.fts_synced_at` 存指纹 | 启动不重建，省 3~5 秒 |
| 补偿 | 指纹对不上时全量重建 | 手改库、恢复备份后能自愈 |

## 3. 查询分流（今天新增）

推理型问句（含「为什么 / 那次 / 后来 / 因为 / 还记得 / 当时 / 结果 / 是不是」等，或长度 ≥ 14 字）**只走语义通道**。

原因：关键词会把"字面相近的邻条"顶上来。评测实测，跨会话推理题 Hit@1 从 70% 掉到 60%；关掉后回到 70%，同时知识更新的收益还在。

## 4. 时间感知

| 规则 | 实现 |
|---|---|
| 时间线索识别 | `_TIME_CUE_RE`：什么时候/哪天/几号/多久/上次/最近/第一次… |
| 新近度加权 | 命中时权重 0.12 → 0.30；回落打分里 0.25 → 0.40 |
| 日期加分 | 正文带具体日期 → +0.12 |

**诚实结论**：合成评测里时间推理题 Hit@1 一直是 70%，加分前后**没有可见提升**——因为带日期的记忆本来就排得进前三。这条规则留着是为了线上长尾（几百条记忆时新近度才会真正起作用），不代表它已经证明有效。

## 5. 事实更新（最容易出错的部分）

### 5.1 检测：同一主题来了新事实

写入路径（`remember` / `ingest` / `ingest_model_pair`）插入新记忆后，调用 `_check_fact_change`：

1. 候选：`kind='fact'` 或正文含「记：」的旧记忆；
2. 命中条件（任一）：
   - **同 subject**（生日/住址/工作/关系这类有明确槽位的）；
   - **同 kind** 且属于可覆盖类型（`location / work / relationship / birthday / preference / pet`）；
   - **同生活领域**（9 个词典：口味 / 作息 / 健康 / 居住 / 工作 / 关系 / 宠物 / 金钱 / 爱好）；
3. 正文完全相同 → 视为重复，不报；
4. 最多同时挂 3 条，避免一次写满。

### 5.2 处理：默认挂起，明确改口才动手

| 情况 | 行为 |
|---|---|
| 一般新事实 | 旧记录**保持 active**，`conflicts` 表插一条 `pending`，`memory_links` 插一条 `evolve` 边（0.6） |
| 正文含明确改口词（戒 / 搬家 / 换成 / 改成 / 不再 / 分手 / 离婚…） | 旧的**立刻** `status='superseded'` 且写 `valid_to`，但 conflict 仍保留，随时可回滚 |

为什么分两种：一般情况分不清"补充"还是"覆盖"，交给人一点；"我戒辣了"这种是明确替换，等到人点确认时，模型可能已经用旧事实答了三次。

### 5.3 有效期（C4）

- 列：`memories.valid_to`（ISO 时间，NULL = 一直有效）。
- 召回 SQL 过滤：`AND (valid_to IS NULL OR valid_to > ?)`。
- 写入点：`supersede()`、明确改口、`resolve_conflict` 的输家。

### 5.4 回滚语义

`resolve_conflict(id, keep_old | keep_new)`：

- 输家 → `superseded` + `valid_to`；
- 赢家 → `active` + `superseded_by=NULL` + `valid_to=NULL`。

两边都维护，避免"点完发现两条都不能用了"。

### 5.5 改写（C8）

`revise(memory_id, new_text, supersede_old=False)`：改正文 → 重建该条 FTS → 重算向量 → 可选让同主题旧记录失效。CLI：`python companion_brain.py --revise 37 --text "…" [--supersede-old]`。

## 6. 排序后处理

| 步骤 | 做法 | 目的 |
|---|---|---|
| 规则重排 | 前 20 条里：查询整句出现在正文 +0.12；查询双字覆盖率 ×0.10 | 短句向量区分度差，精确命中更可信 |
| 拒答 | 只在**非永久**候选里看：最高分 < 0.42 且（最高 − 第三）< 0.06 → 返回空 | 分数低且挤在一起 = 没有真正对得上的；永久记忆不受此限 |
| MMR | 按层配额（core / semantic / episodic），永久记忆先占位 | 防止五条都是同一件事 |
| 联想 | 从已选前两条走一跳共现/演化边，最多补 2 条 | 让"上次那件事"能带出前因 |

## 8. 评测（怎么证明这些规则有用）

工具：`tools/eval_memory.py`，说明文档：`docs/评测集说明.md`。

- **50 题**：信息抽取 / 跨会话推理 / 时间推理 / 知识更新 / 拒答，各 10 道；
- **合成语料**：21 个会话 / 92 条记忆 / 9 条已被替代；
- **指标**：Hit@1/3/5、MRR@5、拒答正确率、门控误伤、端到端正确率；
- **拒答阈值**每次自动标定（18 道校准题，按平衡准确率取切点），不写死；
- **只读**：临时库，或 `mode=ro` + 内存 FTS，绝不写 `brain.db`。

### 四种配置实测（bge-small-zh 512 维，k=5）

| 配置 | 跨会话 Hit@1 | 知识更新 Hit@5 | 总体 Hit@1 | 总体 Hit@5 | MRR | 门控误伤 |
|---|---|---|---|---|---|---|
| 纯向量基线 | 70.0% | 90.0% | 75.0% | 95.0% | 0.825 | 10/40 |
| 融合（无分流） | 60.0% | 100.0% | 72.5% | 97.5% | 0.825 | 10/40 |
| 融合 + 生产规则 | 60.0% | 100.0% | 72.5% | 97.5% | 0.825 | 10/40 |
| **融合 + 生产规则 + 分流** | **70.0%** | **100.0%** | **75.0%** | **97.5%** | **0.831** | **8/40** |

### 两条要记住的结论

1. **关键词通道在强向量下是中性偏负的**：它对信息抽取 +10 个点，对跨会话推理 −10 个点。加了分流才变成全面不劣。
2. **权重越低越好**：alpha 0.1 / 0.2 / 0.3 的 Hit@5 分别是 100% / 97.5% / 97.5%，所以生产从 0.25 下调到 0.18——关键词的价值是**字面兜底**（人名、型号、编号），不是普遍提升。

## 9. 备份与密钥

| 项 | 做法 |
|---|---|
| 脱敏范围 | 按**文件名**匹配 `config.json` / `state.json` / `facts.json`（含 `data/core/backup-*/` 里的历史副本） |
| 脱敏字段 | `apikey / key / secret / token / password / cookie / authorization …` → `***已脱敏***` |
| 原值存放 | `backups/secrets/secrets-<时间>.json`，不在网盘目录内，只留最新 20 份 |
| 历史包清理 | `python data_backup.py scrub <目录或zip>` |
| 恢复注意 | 从包里恢复后要照 secrets 文件把密钥填回去，否则模型连不上 |

**今天真实修掉的两个泄漏点**：

1. 历史包里的 `data/core/backup-p0-*/state.json` 带明文 `sk-`——原实现只匹配固定路径，漏了嵌套副本；
2. 脱敏清单只覆盖 3 个固定路径，`data/core/` 下的副本不在内。

修完复查：6 个历史包「仍含 sk- 的」= 无。

## 12. 已知限制 / 明确不做

| 项 | 状态 |
|---|---|
| 合成评测 95% 不代表线上水平 | 每类 10 道，一道题 = 10 个点，只能做回归比较 |
| 时间加分的效果**未被数据证实** | 保留是为线上长尾，评测里没提升 |
| 关键词在强向量下收益有限 | 已下调权重 + 分流；定位为字面兜底 |
| 拒答 100% 是阈值换来的 | 代价是 8/40 道能答题被误伤，所以同时报误伤数 |
| Ollama 不纳入看门狗 | 云端正常，纳入只多占内存 |
| `strength` 未恢复为历史值 | 原值已丢，改动量在 0.863–0.998，看不出来 |
| 不做记忆正文的深度改写 | 无数据支持，改写内容风险高 |
