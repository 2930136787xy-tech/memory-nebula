# 设计思路：把「记忆」从数据库变成一张可以走进去的星云

> 这份文档只讲**为什么这么做**，不逐行讲代码。想知道每个接口怎么调，看
> [接口说明](./接口.md)；想知道数据表长什么样、怎么部署，看
> [数据与部署](./数据与部署.md)。

## 一句话

聊天机器人每天都在写记忆，但「它到底记住了什么、记错没有、哪些快忘了」一直是个黑箱。
记忆星云把两份记忆库、私聊消息、每日摘要和人格档案合成一张三维力导向图：
**球是数据，大小是重要度，灰度是遗忘程度，线是关系**——看得见，也改得动。

![记忆星云首页](./images/screenshot.png)

## 1. 起点：问题不是「存不下」，而是「看不见」

这个项目原本只是一个 QQ 机器人的附属页面。机器人有两条记忆链路：

| 库 | 谁写入 | 内容 | 特点 |
|---|---|---|---|
| `bridge.db` | 每轮问答实时写 | 用户问 + 机器人答的成对记忆 | 量大，是「共用记忆」，另一个端也在读 |
| `brain.db` | 夜间整理 / 伴生大脑 | 提炼后的事实、情绪、向量、重要度 | 有强度、有半衰期、有语义向量 |

数据一直在增长，但主人能用的只有「召回」：对话时挑几条塞进提示词。问题随之而来：

- 记错了没法改，只能等它被新记忆覆盖；
- 想不起来某件事是在哪次对话里说的；
- 不知道哪些记忆快被遗忘了，哪些被标成了永久；
- 两个库各自为政，看不出「同一个人」在两份库里的记忆是不是一回事。

所以第一版目标非常具体：**给主人一面能照见记忆的镜子**，而不是再做一个后台表格。

## 2. 目标与非目标

**要做：**

1. 一屏看清结构：谁、聊过多少、记忆挂在哪、哪些记忆彼此相似；
2. 一眼看出轻重：重要度、遗忘强度、永久标记；
3. 能直接操作：改正文、调重要度、忘掉/恢复、永久、删除、合并；
4. 能分权：本机全权、只读给朋友看、一人一号只看自己；
5. 手机能开，首屏别超过 1MB；
6. 部署零依赖：只装 Python，不装数据库、不装 Node。

**不做：**

- 不做通用图数据库前端（Neo4j Bloom 那种通用查询语言）；
- 不做多人实时协同编辑；
- 不在页面里跑模型推理或训练；
- 不把「记忆」抽象成万能 schema：字段就是为这两份库长的。

## 3. 为什么是三维力导向图

选型时比较过四种形态：

| 形态 | 优点 | 为什么没选 |
|---|---|---|
| 表格 | 精确、可排序 | 看不出「关系」和「聚类」，而记忆的价值恰恰在关系 |
| 时间线 | 时间顺序清楚 | 记忆是多对多的：一条记忆同时属于人、会话、日期、主题 |
| 二维网络图 | 关系清楚、易读 | 边一多就糊成一团；三层圈层和语义边会互相压盖 |
| 三维力导向 | 聚类自然、有纵深、好看 | 有遮挡和眩晕风险，需要额外做取景与压暗 |

最终选三维，是因为它同时满足三件事：

1. **力导向**把「经常一起出现」的球自然拉在一起，不需要手工布局；
2. **纵深**让不同层（核心/熟识/陌生）可以真的分层，而不是挤在一个平面；
3. **可探索**：旋转、缩放、飞向某个球，比翻表格更接近「回忆」这个动作。

参考的是 [3d-force-graph](https://github.com/vasturiano/3d-force-graph) 的示例，以及
Cosmograph、Neo4j Bloom 这类图分析产品的视觉方向：深色底、高饱和球、亮线。

## 4. 数据怎么变成视觉

视觉编码不是装饰，每一条都对应一个字段：

| 视觉 | 编码的字段 | 规则 |
|---|---|---|
| 颜色 | 节点类型 | 核心金、人格粉、会话蓝、日期紫、消息绿、摘要青、记忆橙 |
| 紫红 | `pinned=1` | 永久记忆单独一个颜色，和「更难忘」的明暗区分开 |
| 大小 | 重要度 / 数量 | 记忆球 = 5 + 4×重要度；会话球随消息数增大；核心球固定 18 |
| 灰度 | 遗忘强度 | `强度 = 0.5^(天数/半衰期)`，`半衰期 = 7 + 83×重要度` 天 |
| 青线 + 流动粒子 | 语义相似 | 摘要↔摘要、摘要↔记忆、记忆↔记忆（共用记忆没有向量，不参与） |
| 橙线 | 被替代 | 旧记忆 → 新记忆（`superseded_by`） |
| 蓝线 | 归属 | 消息 → 会话，数量最多 |
| 紫线 + 粒子 | 活跃 | 会话在某天有对话 |
| 粉线 | 拥有 | 人格 → 私聊会话 |
| 浅蓝线 | 摘要 | 会话↔摘要、日期↔摘要 |
| 弧线 | 多重关系 | 同一对球有多条边时错开，不叠成一条直线 |
| 悬停压暗 | 聚焦 | 只亮它和邻居，其余降到 45% 亮度 |

两条经验：

- **颜色只编码类型**，不再编码重要度。早期试过用颜色深浅表示强度，结果和「永久」的紫红打架，
  最后改成「大小=重要度、灰度=强度」，两个维度互不干扰。
- **弧线是必须的**。一个会话和一个日期之间可能同时有「活跃」「摘要」两条边，
  不弯曲就会重合，看起来像只有一条。

三层圈层用固定半径锚定（核心 94、熟识 176、陌生 304），力导向只负责圈内的微调：

```
        outer 304    陌生 / 暂时不熟
      inner 176      同学、熟人
    core 94          管理员、系统核心
```

这样「关系远近」是稳定的，不会因为某天多聊了几句就把一个人甩到图外。

## 5. 空间与镜头

图的范围能到 ±400 单位，而 3d-force-graph 的初始镜头距离只有 320——不处理的话，
一半的球一开始就在视野外。所以加载完成和引擎停止时各调一次 `zoomToFit()`。

另外做了三个镜头相关的功能：

- **回中心**（Home / 0）：把镜头拉回全图中心，迷路时用；
- **二维平铺**：只看一个人时，把记忆铺成网格，方便逐条读；
- **星云模式**：纯展示态，球散开、缓慢自转、关系线上有光点脉冲，适合投屏或截图。

星云模式和操作模式是两套相机参数，共用同一份图数据，切换不重建。

## 6. 交互：从「看」到「改」

页面上的每个按钮都对应一个真实痛点：

| 功能 | 解决的痛点 |
|---|---|
| 搜索 | 记得一句话，想不起它属于谁 |
| 看谁 | 人一多，图太密；只看一个人时自动框住这一团 |
| 时间轴 | 想找「上个月」发生的事 |
| 图例筛选 | 消息球太多挡住记忆球，按类型关掉 |
| 详情面板 | 看全文、看来源（共用/本地）、看重要度、看时间 |
| 多选 + 批量条 | 一次忘掉/永久/合并一批记忆，而不是一条条点 |
| 同步 | 后台每 30 分钟才重建一次，改完想立刻看到 |
| 导出 | 把记忆导出成 JSON，换机器或备份 |
| 说明 | 视觉编码太多，必须有一页能查 |

一个细节：**写操作后自动重建 `graph.json`**，页面再重新拉一次。用户不需要理解
「重建」这件事，点「保存」就该看到球变了。

批量操作只对记忆球生效，而且前端会先按 `mine` 过滤，服务端再按归属校验一次——
前端隐藏按钮只是体验，真正的权限在服务端。

## 7. 数据层：两份库，一种 id

图里的记忆节点 id 是 `mem:<库>:<id>`：

- `mem:s:9` → `bridge.db` 的第 9 条（共用记忆）
- `mem:b:9` → `brain.db` 的第 9 条（本地伴生）

这样做的好处是：**前端不用知道有几个库**，只传 id；服务端按前缀路由到对应的库。
两库的时间单位还不一样（bridge 是毫秒，brain 是秒），在 `memory_view.py` 里统一成秒。

### 语义边怎么算才不炸

记忆两两算余弦是 O(n²)：1000 条要 27 秒。这里做了三层控制：

1. **粗排**：每 8 维取一维，先挡掉明显无关的；
2. **精算**：粗排过线的才算完整余弦；
3. **限量**：记忆↔记忆只比最近 120 条，摘要全参与。

相似度还做了基线校正：`(cos - 0.45) / 0.55`，和召回用的是同一套口径。
向量用 base64(float32) 缓存，比 JSON 数组小约 5 倍；算过一次就离线可用。

## 8. 权限：三种模式，一套代码

| 模式 | 启动方式 | 能看到 | 能改 | 适合 |
|---|---|---|---|---|
| 本机 | `start-viewer.bat`（8765，只绑 127.0.0.1） | 全部 | 全部 | 自己用 |
| 只读 / 访客 | `start-viewer-readonly.bat`（8766，`--guest`） | 完整拓扑，正文全部抹掉 | 不能 | 演示、截图、给人看个大概 |
| 账号 | `start-viewer-accounts.bat`（8767，`--accounts`） | 完整拓扑；自己的正文完整，别人的抹掉 | 只能改自己的；管理员全权 | 一小群朋友 |

关键设计是**「抹掉」和「裁剪」分开**：

- `overview_graph()`：保留全部球和边（所以能看到「这个人有多少记忆」），
  但把别人的 `text/fact/label` 换掉，打上 `redacted`；
- `scope_graph()`：只保留「他自己」那一团——人格球、私聊、私聊里的消息/摘要/记忆；
- `guest_graph()`：等于 `overview_graph("")`，没有任何 `mine`，前端不会出现编辑入口。

服务端的写接口再按 `owner` 校验一次：普通账号只能改 `private:<自己>` 的共用记忆和
`speaker=<自己>` 的本地记忆，越权直接 403。导出同理，只导出自己的。

> 访客模式下，`meta.people`（「看谁」下拉里的昵称）也会被清空——昵称本身也是个人信息，
> 早期版本漏了这一点，现在已修。

## 9. 性能：首屏从 1.7MB 降到 0.45MB

| 优化 | 做法 | 效果 |
|---|---|---|
| 动态 gzip | 超过 1KB 的 HTML/JSON 响应现场压缩 | 首页 71KB→25KB，`api/graph` 263KB→47KB |
| 预压缩 vendor | 大库旁边放 `.gz`，命中就直接发 | 3d-force-graph 1.39MB→364KB |
| 长缓存 | `vendor/*` 加 `immutable`，URL 带 `?v=N` 换版本 | 第二次打开直接走缓存 |
| 页面不缓存 | HTML/JS/CSS/JSON 一律 `no-store` | 改完刷新立刻生效 |
| 原子写 | `graph.json` 先写临时文件再替换 | 重建时刷新也不会读到半个 JSON |

首屏从约 1.7MB 降到约 0.45MB。图的规模在 300~400 个节点时仍然流畅；
再大就需要考虑按人裁剪、增量渲染或 WebGL 实例化，这是下一步的事。

## 10. 安全：默认只绑 127.0.0.1

这是个人数据，默认配置必须「别人连不上」：

- 默认只监听 `127.0.0.1`，局域网和公网都进不来；
- 写接口要求自定义头 `X-Viewer: 1`——跨站表单带不了这个头，跨域又会先 OPTIONS（服务不返回 CORS），
  比只靠 `SameSite=Lax` 更稳；
- 响应头带 CSP、`nosniff`、`DENY`、`no-referrer`、`Permissions-Policy`，HTTPS 时加 HSTS；
- 账号密码 PBKDF2-SHA256（20 万次迭代），只存哈希；另有一份用本机密钥加密的副本，仅管理员可看；
- 登录按 QQ 限流：10 分钟错 8 次就暂时拒绝，校验故意慢 0.25 秒；
- 请求体上限 2MB，批量最多 500 条，同步最小间隔 5 秒；
- 会话存在服务进程内存里，默认 7 天过期，重启后需要重新登录。

**明文 HTTP 是明确边界**：局域网模式不加密，密码会在链路上裸奔。要公网访问，
请套 HTTPS 反向代理或组网工具，不要把 8767 直接映射到公网。细节见
[数据与部署](./数据与部署.md) 的「公网访问」。

## 11. 踩过的坑

这些都是实际调试出来的，写在这里免得下一个人再花一晚上：

1. **`nodeOpacity(fn)` 不生效**：这个版本的 3d-force-graph 只接受数字，传函数会让所有球变全透明，
   看起来就是「黑屏、球不见了」。想表达强度请改颜色。
2. **`backgroundColor('rgba(0,0,0,0)')` 会变纯黑**：three.js 解析不了透明色，回退成不透明黑，
   把 CSS 星尘全盖住。背景用不透明色，星云用 `mix-blend-mode: screen` 的叠加层。
3. **不要用 PowerShell 的 `Set-Content` / `-replace` 改源码**：默认按 ANSI 读写，中文会变乱码
   （踩过两次）。用支持 UTF-8 的编辑器，改完跑一次编码检查。
4. **`graph2ScreenCoords()` 返回的坐标是错的**：节点在屏幕中间，它却给 `y=-700`。
   要做 HTML 叠加层，自己用 `camera.projectionMatrix × matrixWorldInverse` 算。
5. **镜头不会自动取景**：初始距离 320，图能到 ±400，必须手动 `zoomToFit()`（加载后和引擎停止时各一次）。
6. **换了 vendor 的 JS 要同时重做 `.gz` 并改 `?v=`**：否则浏览器可能继续用旧缓存，
   或者服务端发出的 gzip 和文件名对不上。

## 12. 取舍清单

| 决定 | 代价 |
|---|---|
| 单文件 `web/index.html`（约 2700 行） | 没有构建步骤，改完刷新即生效；但文件很大，改之前先搜 |
| vendor 冻结在本地 UMD 包 | 离线可用、无 CDN；但包没暴露 `THREE`，做不了 bloom/自定义着色器 |
| 两份记忆库保持独立，只在图里合并 | 不破坏机器人现有写入逻辑；语义上仍要记得「有两个库」 |
| 全量重建 `graph.json` | 逻辑简单、结果一致；数据量再大就需要增量 |
| 会话放内存 | 不落盘、泄露面小；重启后所有人重新登录 |
| 不内置 HTTPS | 依赖部署方加反代；但默认只听 127.0.0.1，风险可控 |

## 13. 下一步

1. **换 ESM 版 three + 3d-force-graph**，暴露 `THREE` 后做菲涅尔发光球和 `UnrealBloomPass`，
   现在只有「大球 + 高饱和 + 光照」，没有外发光；
2. **时间轴播放**：按天推进，看记忆怎么长出来、怎么变灰；
3. **冲突可视化**：同一事实的新旧版本做并排 diff，而不是只在「核心候选」里列文字；
4. **增量重建**：只重算变化的节点，支持更大的库；
5. **审计**：谁在什么时候改了哪条记忆，留一份可追溯的日志。

## 14. 代码怎么读

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 1 | `memory_view.py` | 数据怎么变成节点和边；权限裁剪也在这里 |
| 2 | `viewer_server.py` | 路由、鉴权、写接口、gzip 和缓存 |
| 3 | `web/index.html` | 视觉编码、交互、相机 |
| 4 | `accounts.py` | 账号、密码哈希、密钥 |
| 5 | `core_api.py` / `core_life.py` | 「数字生命」后台页（可选） |
| 6 | `demo/make_demo.py` | 没有真实数据时怎么造一套可跑的演示 |

数据流：

```
bridge.db ─┐
brain.db ──┤
data/*.json├─→ memory_view.build() ─→ web/graph.json ─→ viewer_server ─→ 浏览器
personas/ ─┤                              ↑
config.json┘                        写操作后自动重建
```
